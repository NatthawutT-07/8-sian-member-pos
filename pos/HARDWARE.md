# WORREX JP80H + ลิ้นชัก + บาร์โค้ด

อุปกรณ์ที่ตรวจจริง: `JP80H-UBW_BD41`, กระดาษกว้างประมาณ 78 มม. (กลุ่ม 80 มม.), ลิ้นชัก WORREX ที่ต่อกับเครื่องพิมพ์ ผู้ใช้ยืนยันเมื่อ 1 พฤศจิกายน 2026 ว่าใบเสร็จภาษาไทย/บาร์โค้ดพิมพ์ชัดครบ และลิ้นชักเปิดด้วยคำสั่ง 200 ms แล้ว

## เริ่มใช้งาน

1. เปิด backend เดิม แล้วเปิดโปรแกรม **8 Sian POS** รุ่น 0.2.0 จาก `pos/release/win-unpacked/8 Sian POS.exe` หรือใช้ตัวติดตั้งใน `pos/release/` โปรแกรมต้องเชื่อม backend ได้ตาม `server.json`
2. เข้าด้วยบัญชีพนักงาน POS จากนั้นกด **อุปกรณ์ → ค้นหาเครื่องพิมพ์ → JP80H-UBW_BD41 → เชื่อมต่อ** หากไม่พบ ให้เปิดเครื่องพิมพ์และเพิ่มอุปกรณ์ใน Bluetooth ของ Windows ก่อน ชื่อและการเลือกเครื่องบันทึกใน `hardware.json` ในโฟลเดอร์ข้อมูลโปรแกรม
3. กด **พิมพ์ทดสอบภาษาไทยและบาร์โค้ด** ตรวจตัวอักษร ขอบกระดาษ และการตัดกระดาษ ใบทดสอบไม่สร้างยอดขาย
4. ต่อสายลิ้นชักเข้าช่อง Cash Drawer ของเครื่องพิมพ์ ปลดกุญแจจากตำแหน่งล็อก กรอกเหตุผล เช่น `ทดสอบลิ้นชัก` แล้วกด **เปิดลิ้นชัก** ใช้ช่องมาตรฐานขา 2 ก่อน ช่องสำรองขา 5 มีไว้สำหรับสายที่ต่ออีกขาหนึ่ง
5. เมื่อทดสอบลิ้นชักสำเร็จ เลือก **เปิดลิ้นชักเฉพาะเงินสด** และ **บันทึกการตั้งค่า** ค่าเริ่มต้นบนเครื่องใหม่ปิดตัวเลือกนี้ไว้ เครื่องที่ยืนยันการทดสอบแล้วสามารถบันทึกเปิดใช้งานได้
6. เลือกสินค้าใน **พิมพ์บาร์โค้ดสินค้า CODE128** แล้วกด **พิมพ์บาร์โค้ด 1 ใบ** ใช้รหัสสินค้าจากแอดมิน หากยาวเกินพื้นที่พิมพ์ ระบบแจ้งให้ย่อรหัสแทนการบีบเส้นจนสแกนไม่ได้
7. เครื่องสแกนตั้งเป็น HID keyboard และ Enter suffix จากนั้นวางโฟกัสที่ช่องสินค้า/สมาชิกหรือคูปองแล้วสแกน ทดสอบเครื่องสแกนจริงอีกครั้งก่อนเปิดขาย

## พฤติกรรมขณะขาย

- บันทึกชำระกับ backend สำเร็จก่อนสั่งอุปกรณ์ เงินสดเปิดลิ้นชักก่อนพิมพ์เมื่อเปิดตัวเลือกไว้ โอนเงินไม่เปิดลิ้นชัก
- พิมพ์ซ้ำจากบิลเดิมไม่เปิดลิ้นชัก ไม่สร้างยอดขาย และไม่หักคูปองหรือเพิ่มครั้งสมาชิกอีก
- งานอุปกรณ์ทำทีละงาน หากเครื่องปิด/ขาดการเชื่อมต่อ ระบบแจ้งข้อผิดพลาดโดยยังเก็บบิลที่ชำระแล้วไว้ หากกระดาษออกบางส่วนให้ตรวจเครื่องก่อนกดพิมพ์ซ้ำ ไม่มีการ retry งานพิมพ์/ลิ้นชักเองหลังส่งค้าง
- การรับคำสั่งของ Bluetooth ไม่ใช่หลักฐานว่ากระดาษออกหรือลิ้นชักเปิด ต้องตรวจอุปกรณ์จริง
- ต้องมีเซสชันพนักงาน USER ที่ยังใช้งานได้และเซิร์ฟเวอร์ออนไลน์ก่อนสั่งงาน audit เก็บผู้ใช้ เหตุผล เลขบิลเมื่อเกี่ยวข้อง และสถานะ REQUESTED / SENT / FAILED_OR_UNKNOWN โดยไม่เก็บเนื้อหาใบเสร็จหรือรหัสสมาชิกดิบ
- Claim คำสั่งอัตโนมัติใช้ primary key ของ AuditLog แบบเฉพาะบิล กันการเปิดซ้ำจาก checkout retry และหลายเครื่อง ใช้กับบิลเจ้าของบัญชีที่เพิ่งชำระไม่เกิน 15 นาที หากแอปปิดหลัง claim ก่อนสั่งงาน ให้ใช้พิมพ์ซ้ำ/เปิดด้วยตนเองพร้อมเหตุผล

## รายละเอียดสำหรับดูแลระบบ

- BLE GATT service `18F0`, write characteristic `2AF1`, เขียนแบบได้รับคำตอบรับ ใช้ ATT MTU ที่ Windows เจรจาได้ สูงสุด 180 ไบต์ต่อครั้ง และ fallback 20 ไบต์เมื่อ MTU=23
- ภาษาไทย/โลโก้เรนเดอร์ใน Chromium แล้วส่งภาพขาวดำ ESC/POS `GS v 0` กว้าง 576 จุด ไม่พึ่ง code page ของเครื่องพิมพ์ CODE128 มี quiet zone และความกว้างเส้นอย่างน้อย 2 จุด
- ลิ้นชักที่ทดสอบได้ใช้ `ESC @` ตามด้วย `ESC p 48 100 250`: 200 ms ON, 500 ms OFF ที่ขา 2 คำสั่งพัลส์ 100 ms ที่ทดลองก่อนหน้าไม่เปิดลิ้นชักเครื่องนี้
- PowerShell 5.1 / WinRT ใช้เฉพาะ Windows ไม่มีการดาวน์โหลดหรือรันโปรแกรมจากเว็บขณะพิมพ์ ส่งเนื้อหาผ่าน stdin ไม่ใส่ใน command line หรือไฟล์ใบเสร็จชั่วคราว
- Hardware bridge ใช้ preload จำกัดคำสั่ง ยืนยัน top-level frame/origin ที่ตั้งไว้ และอ่านบิล/สินค้าจาก API ที่มีเซสชัน ไม่รับ raw bytes หรือยอดขายจาก renderer มาสั่งโดยตรง
- Browser Chrome/Edge ยังใช้หน้าต่างพิมพ์ Windows; BLE bridge มีเฉพาะโปรแกรม Electron ไม่เปิดบริการควบคุมเครื่องบนพอร์ต HTTP สาธารณะ
- ไม่ต้องมี migration ใหม่สำหรับชุดนี้ ใช้ AuditLog ที่มีอยู่ แต่ต้องอัปเดต backend และ `pos/web` พร้อมโปรแกรม desktop

## ตรวจซอฟต์แวร์

จาก root: `npm.cmd test -w backend`, `npm.cmd test --prefix pos`, `npm.cmd run check:render --prefix pos`, `npm.cmd run check:hardware-ui --prefix pos`

ชุด UI ใช้ API/ฮาร์ดแวร์จำลอง ไม่แตะยอดขายหรืออุปกรณ์จริง ตัวอย่างภาพอยู่ `.tmp/pos-hardware/` สร้างตัวติดตั้งด้วย `npm.cmd run build:pos` ตัวติดตั้งยังไม่มีใบรับรอง code signing ของร้าน
