# สั่งอาหารผ่าน QR ประจำโต๊ะ

## หน้าพ่อครัวใน POS

- แอดมินเปิด **พนักงานและสินค้า POS** แล้วสร้างบัญชี เลือกหน้าที่ **พ่อครัว (CHEF)** หรือแก้บัญชีเดิมให้เป็น CHEF การเปลี่ยนหน้าที่จะยกเลิก session เดิม ให้เข้าสู่ระบบใหม่
- ใช้แอป POS เดิม ล็อกอินด้วยบัญชี CHEF แล้วจะเข้าหน้า **ออเดอร์รอทำ** ทันที คิวเรียงจากเก่าไปใหม่ อัปเดตทุก 5 วินาที และโหลดเองได้
- กด **ยอดอาหารสำเร็จ** บนออเดอร์ หรือเลือกโต๊ะที่ยังมีลูกค้าอยู่จากแถบด้านบนเพื่อดูจำนวนอาหารที่กดสำเร็จแล้วของบิล/รอบโต๊ะปัจจุบัน ไม่นับและไม่แสดงรายการรอทำในยอดรวมนี้ โต๊ะที่ปิดแล้วจะหายจากรายการให้เลือก
- กด **สำเร็จแล้ว** เพื่อบันทึกออเดอร์นั้นเป็น DONE และเอาออกจากคิว การกดซ้ำไม่เพิ่มจำนวนสะสม
- เมื่อพนักงานคิดเงินปิดโต๊ะ รายการค้างของรอบนั้นจะถูกยกเลิก หน้าพ่อครัวเอาโต๊ะออกและปิดสรุปรอบเดิมในการโหลดครั้งถัดไป เปิดโต๊ะรอบใหม่เริ่มยอดจากศูนย์
- กด **พิมพ์ใบอาหาร** เพื่อพิมพ์เลขโต๊ะ รหัสออเดอร์ เวลา และชื่ออาหารพร้อมจำนวน แบบกะทัดรัด พื้นที่ข้อความประมาณ 50 มม. ไม่มีโลโก้/ยอดเงิน/บาร์โค้ด ใช้เครื่องพิมพ์ที่ตั้งค่าไว้ใน **อุปกรณ์** หากเปิดผ่านเว็บจะมีหน้าตัวอย่างและปุ่มพิมพ์ผ่านเบราว์เซอร์ การพิมพ์ไม่เปลี่ยนสถานะออเดอร์
- บัญชี CHEF ไม่มีสิทธิ์คิดเงิน ดูยอดขาย ปิดโต๊ะ หรือเปิดลิ้นชัก ทั้ง API และคำสั่งอุปกรณ์ตรวจสิทธิ์ บัญชี USER ยังใช้ POS เดิมได้

ต้องปิดและเปิดแอป POS ใหม่เพื่อโหลด preload/คำสั่งเครื่องพิมพ์ใหม่ ส่วน Android ต้อง rebuild แอปหลังอัปเดต bridge Migration ของสิทธิ์พ่อครัวคือ `202611020004_chef_role` ไม่ต้อง generate Prisma Client ใหม่เพราะ role เป็น String เดิม

## ขั้นตอนใช้งาน

1. แอดมินเปิดแท็บ **โต๊ะและเมนูสั่งอาหาร** เพิ่มช่วงหมายเลขโต๊ะ แล้วดาวน์โหลด QR ไปติดตามโต๊ะ การเพิ่มช่วงที่ครอบคลุมโต๊ะเดิมจะไม่เปลี่ยน QR เดิม ไม่มี API ลบโต๊ะหรือเปลี่ยน QR
2. เพิ่มเมนูตาม **โซน → หมวดหมู่ → รายการ** เช่น เนื้อสัตว์ → หมู → หมูสามชั้น หรือ ทะเล → กุ้ง → กุ้งสด เมนูสั่งอาหารแยกจากสินค้าที่ใช้คิดเงิน POS

   เพิ่มรูปอาหารได้ในฟอร์มเพิ่ม/แก้ไขเมนู เลือก JPG, PNG หรือ WebP ต้นฉบับไม่เกิน 15 MB ระบบย่อด้านยาวไม่เกิน 1,200 พิกเซลและแปลงเป็น JPEG ก่อนอัปโหลดไม่เกิน 2 MB มีตัวอย่างก่อนบันทึก เปลี่ยนรูปหรือนำรูปออกได้ รูปเป็นตัวเลือก เมนูไม่มีรูปยังสั่งได้ตามปกติ รูปเก็บในฐานข้อมูลและอยู่ในการสำรองฐานข้อมูลด้วย ต้องตั้ง proxy ให้รับ request ได้อย่างน้อย 2 MB และรัน migration `202611020002_ordering_images`
3. พนักงานเพิ่มสินค้าและรับชำระเงินได้โดยไม่บังคับเลือกโต๊ะ หากต้องการเปิดสั่งอาหารผ่าน QR ให้เลือกโต๊ะว่างก่อนยืนยันรับเงิน บิลไม่ระบุโต๊ะจะไม่เปิดโต๊ะหรือแสดงหน้าต่างเลือกโซน
4. เมื่อบันทึกบิลสำเร็จ ระบบจองรอบโต๊ะและแสดงหน้าต่างเลือกสิทธิ์โซน เลือกได้หลายโซนหรือไม่เลือกเลยก็ได้ แล้วกด **ยืนยันสิทธิ์และเปิดโต๊ะ** ถ้าไม่เลือกโซนจะเปิดหน้าโต๊ะได้แต่ไม่มีรายการอาหารให้สั่ง
5. ถ้าปิดหน้าต่างหรือโหลดโซนไม่สำเร็จ โต๊ะจะยังสั่งไม่ได้ เปิดเมนู **โต๊ะ / ออเดอร์อาหาร** แล้วกด **เลือกโซน / เปิดโต๊ะ** เพื่อทำต่อ ห้ามรับเงินซ้ำ
6. ลูกค้าสแกน QR เดิม เลือกโซน หมวดหมู่ และจำนวนอาหาร ตรวจรายการที่กำลังจะส่งแล้วกดส่ง เมื่อส่งสำเร็จตะกร้าจะว่าง ไม่มีหน้าประวัติและไม่มี API ประวัติสำหรับลูกค้า
7. พนักงานเปิด **โต๊ะ / ออเดอร์อาหาร** ดูรายการรอดำเนินการ หน้าต่างอัปเดตทุก 15 วินาที กด **ดำเนินการแล้ว** เมื่อจัดการรายการนั้นเรียบร้อย
8. เมื่อลูกค้าออก กด **ลูกค้าออกแล้ว / ปิดสั่งอาหาร** และยืนยัน การส่งใหม่จะถูกปิดที่เซิร์ฟเวอร์ทันที รายการที่ยังรอดำเนินการของรอบนี้จะเปลี่ยนเป็น `CANCELLED` และออกจากคิวพร้อมกับปิดโต๊ะ รายการที่ดำเนินการแล้วและโต๊ะอื่นคงเดิม หน้าลูกค้าล้างตะกร้าและรายการรอยืนยันเมื่อพบว่าโต๊ะปิด ตรวจทุก 10 วินาทีและเมื่อกลับมาที่หน้าต่าง จึงอาจแสดงหน้าค้างชั่วคราว แต่เซิร์ฟเวอร์จะไม่รับคำสั่งใหม่หลังปิดโต๊ะ

ลูกค้ารอบใหม่ต้องชำระเงินและเลือกสิทธิ์โซนใหม่ QR ของโต๊ะยังเป็นรูปเดิม สิทธิ์รอบเก่าไม่ย้ายมารอบใหม่ และการส่งบิลเดิมซ้ำไม่เปิดโต๊ะที่ปิดแล้ว

## เตรียมระบบ

### จำกัดพื้นที่ส่งออเดอร์

หน้าลูกค้าขอตำแหน่งใหม่ทุกครั้งก่อนส่งรายการ รวมถึงการส่งรายการเดิมซ้ำ เซิร์ฟเวอร์รับเฉพาะพิกัดภายในรัศมี 200 เมตรจาก `13.944698337170372, 100.54483398858625` พิกัดต้องอายุไม่เกิน 30 วินาทีและรายงานความคลาดเคลื่อนไม่เกิน 100 เมตร หากไม่อนุญาตตำแหน่ง อ่านไม่ได้ หรืออยู่นอกพื้นที่จะส่งไม่ได้ แต่ยังเปิดเมนูได้ QR, URL และรหัสโต๊ะเดิมไม่เปลี่ยน

ต้องใช้งานผ่าน HTTPS และอนุญาตตำแหน่งในเบราว์เซอร์/ระบบมือถือ พิกัดมาจากอุปกรณ์ จึงไม่ใช่การป้องกันการปลอม GPS ได้ทั้งหมด ไม่เก็บพิกัดลงฐานข้อมูล และไม่นำพิกัดมาคำนวณรหัสตรวจรายการซ้ำ อัปเดต backend และ frontend คู่กัน ไม่ต้อง migrate ฐานข้อมูล ทดสอบมือถือจริงทั้งในร้าน นอกรัศมี และกรณีปฏิเสธสิทธิ์ก่อนเปิดใช้งาน

ตั้ง `FRONTEND_ORIGIN` เป็นโดเมนเว็บลูกค้าที่จะใช้ถาวรก่อนดาวน์โหลด QR สำหรับพิมพ์จริง (อย่าใช้ localhost) QR เก็บ URL `/order/<opaque-table-token>` โดเมนนี้และข้อมูล `DiningTable.qrToken` ต้องเก็บรักษาไว้ หากย้ายเว็บต้องรักษา URL เดิมหรือทำ redirect และสำรองฐานข้อมูลตามปกติ

จากรากโปรเจกต์บน Windows:

```powershell
npm.cmd run generate -w backend
npm.cmd run migrate -w backend
npm.cmd run build
```

ปล่อย backend และ frontend รุ่นเดียวกัน อัปเดต POS ให้มี `web/table-ordering.js` และหน้าต่างเลือกโซนด้วย เซิร์ฟเวอร์ที่ให้บริการ frontend ต้องรองรับ SPA fallback สำหรับ `/order/*` เช่นเดียวกับหน้าเว็บเดิม ระบบต้องออนไลน์เพื่อยืนยันการรับเงิน เปิดสิทธิ์ ส่งอาหาร และปิดโต๊ะ

Migration ใหม่คือ `202611020001_table_ordering` เพิ่มตารางโต๊ะ เมนู และออเดอร์ พร้อมข้อมูลโต๊ะบนบิลเก่าแบบ nullable การทดสอบไม่ได้ migrate ฐานข้อมูลแอปจริงให้โดยอัตโนมัติ

## การตรวจสอบ

```powershell
npm.cmd test
npm.cmd --prefix pos test
npm.cmd run build
cd backend
node --env-file=.env scripts/check-table-ordering.mjs
```

สคริปต์สุดท้ายรับเฉพาะ PostgreSQL บน loopback สร้าง schema ทดสอบสุ่ม รัน migrations ทั้งหมด ทดสอบ API และธุรกรรมจริง แล้วลบเฉพาะ schema ที่สร้างเอง รองรับ `TEST_DATABASE_URL` หากต้องการแยกฐานทดสอบ ต้อง generate Prisma Client ก่อนใช้งาน

ครอบคลุม QR เดิมเมื่อเพิ่มโต๊ะ สิทธิ์แอดมิน/พนักงาน การชำระเงินที่ล้มเหลว การรอเลือกโซน การเลือกหลายโซน/ไม่มีโซน การป้องกันข้ามโซน คิวพนักงาน การส่งซ้ำพร้อมกัน การปิดโต๊ะกับคำสั่งที่กำลังส่ง การป้องกันรอบเก่า และ rollback เมื่อบันทึก audit ล้มเหลว

## ขอบเขตของ QR คงที่

การปิดโต๊ะบล็อกคำสั่งใหม่ที่ backend ไม่ได้เพียงซ่อนปุ่ม หน้าเดิมจะอัปเดตสถานะภายในรอบตรวจสอบ 10 วินาทีเมื่อออนไลน์ แต่ส่งไม่ได้ทันทีที่โต๊ะปิดแล้ว การยืนยันรอบและรายการอยู่ในธุรกรรม Serializable เพื่อให้คำสั่งที่ชนกับการปิดโต๊ะไม่หลุดเข้าเป็นคำสั่งหลังปิด รายการค้างถูกยกเลิกและออกจากคิว โดยยังมีข้อมูลสถานะยกเลิกสำหรับตรวจสอบภายในและป้องกันการส่งซ้ำ ไม่แสดงประวัติแก่ลูกค้า

QR คงที่เป็นลิงก์ที่แชร์หรือถ่ายรูปเก็บได้ บุคคลที่มีลิงก์ยังเปิดหน้าเมนูและเริ่มส่งได้เมื่อโต๊ะเปิดรอบใหม่ การตรวจ session ป้องกัน payload จากรอบเก่า แต่ไม่พิสูจน์ว่าผู้ที่เปิดลิงก์ใหม่อยู่ที่โต๊ะจริง หากต้องการข้อจำกัดนี้ ต้องเพิ่มรหัสเข้าร่วมรายรอบหรือการอนุมัติอุปกรณ์จากพนักงาน โดยยังใช้ QR เดิมได้
