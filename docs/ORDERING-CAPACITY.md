# ลดโหลดเมนูและป้องกันออเดอร์ซ้ำสำหรับลูกค้า 100 คน

## การโหลดข้อมูล

- หน้าเว็บโหลดเมนูครั้งแรก แล้วตรวจเฉพาะสถานะโต๊ะและเวอร์ชันเมนูทุก 60–70 วินาทีเมื่อมองเห็นหน้าเว็บ ใช้เวลาสุ่มเพื่อลดคำขอที่มาพร้อมกัน
- เมื่อสลับกลับมาที่หน้าเว็บหรือออนไลน์อีกครั้ง จะตรวจสถานะหากห่างจากครั้งก่อนอย่างน้อย 30 วินาที เมื่อซ่อนหน้าเว็บจะไม่ส่งคำขอตรวจตามรอบ
- โหลดรายละเอียดเมนูใหม่เมื่อเวอร์ชันเมนูหรือรอบโต๊ะเปลี่ยน ตะกร้าที่ยังสั่งได้คงเดิม หากเมนูหมดจะนำออกพร้อมข้อความให้ตรวจรายการ
- เมนูเก็บใน sessionStorage อายุ 10 นาที เมื่อโหลดหน้าใหม่ต้องตรวจสิทธิ์โต๊ะและเวอร์ชันกับ server ก่อนนำเมนูที่เก็บไว้ออกมาแสดง
- Backend แชร์แค็ตตาล็อกใน process เดียวกัน 60 วินาที รวมคำขอที่มาพร้อมกันให้ใช้การโหลดเดียว แค็ตตาล็อกไม่รวมรูปแบบ binary และจะกรองโซนตามสิทธิ์โต๊ะที่อ่านสดทุกคำขอ
- หลังแก้เมนู หมวดหมู่ ลำดับหรือรูป จะล้างแคชใน process ที่รับการแก้ไข process อื่นจะหมดอายุแคชภายใน 60 วินาที ลูกค้าตรวจตามรอบจึงอาจเห็นการแก้ไขภายในประมาณ 2 นาที แต่การส่งออเดอร์ตรวจฐานข้อมูลจริงเสมอ
- รูปใช้ URL ที่มีเวอร์ชันและ browser cache แบบ immutable พร้อมแคชบน server จำกัด 64 รูป/16 MB ต่อ process ลดการอ่านรูปซ้ำจากฐานข้อมูล
- Prisma ใช้ connection pool เริ่มต้น 10 connections ต่อ API process และ pool timeout 10 วินาที หากกำหนดใน DATABASE_URL ไว้แล้วจะใช้ค่าที่กำหนด จำนวน process รวมกับบริการอื่นต้องอยู่ในจำนวน connections ที่ PostgreSQL รองรับ

## ความถูกต้องและการกันสแปม

- ใช้ idempotency key เดิมสำหรับคำขอที่ผลยังไม่แน่นอน เก็บไว้จน server ยืนยัน ไม่สร้างคำขอใหม่อัตโนมัติเมื่อเน็ตขัดข้องหรือได้รับ 429
- คำขอใหม่ของโต๊ะเดียวกันต้องห่างอย่างน้อย 5 วินาที และไม่เกิน 12 รายการในหน้าต่าง 60 วินาที ตัวนับอยู่ในฐานข้อมูล ทำงานร่วมกันได้เมื่อมีหลาย API process หรือมีการรีสตาร์ต
- ออเดอร์เดิมที่บันทึกสำเร็จแล้วสามารถตรวจผลด้วย key เดิมได้ โดยไม่ใช้โควตาออเดอร์ใหม่
- จำกัดคำขอส่งรวมต่อ QR โต๊ะ 60 ครั้ง/นาที และคำขอเมนู/สถานะ/ส่งรวมต่อ IP 1,800 ครั้ง/นาที เพื่อให้ลูกค้า 100 คนที่ใช้ Wi-Fi เดียวกันไม่ถูกนับรวมกับโควตาบัญชีสมาชิก 90 ครั้ง/นาที รูปจำกัดแยก 6,000 ครั้ง/นาที/IP
- เมื่อถูกพักการส่ง API ตอบ 429 พร้อม Retry-After หน้าเว็บแสดงเวลารอและเก็บออเดอร์เดิมไว้
- ทุกคำขอส่งตรวจ GPS, รอบโต๊ะ, สิทธิ์โซน, เมนูที่ยังเปิดขาย และจำนวนตามข้อจำกัดเดิม ไม่ใช้เมนูจากแคชตัดสินการรับออเดอร์
- ใช้ conditional row update ใน transaction เพื่อประสานคำขอของโต๊ะเดียวกันกับการปิดโต๊ะ การ retry เมื่อเกิดการแข่งขันใช้ key เดิมเสมอ ไม่รับออเดอร์ซ้ำ

## นำขึ้นระบบ

Deploy backend และ frontend พร้อมกัน โดยทำ backend ก่อน:

```bash
cd ~/8-sian-member-backend
git status --short
git pull --ff-only origin main
pm2 stop 8sian-backend
npm ci && npm run generate && npm run migrate && pm2 restart 8sian-backend --update-env
curl --fail-with-body https://api.8sianracha.com/api/health
```

สำรองฐานข้อมูลตามขั้นตอนเดิมก่อน migration รอบนี้ `202611100003_ordering_throttle` เพิ่มตัวนับใน DiningTable คงค่า .env เดิมและห้ามใช้ migrate reset เมื่อ backend พร้อมแล้วจึง deploy frontend ใหม่

## ผลทดสอบในเครื่องพัฒนา

ใช้ PostgreSQL จริง, pool 10 connections, schema ชั่วคราวที่แยกจากเมนู/โต๊ะจริง และ API สอง instance:

| กรณี | ผล |
| --- | --- |
| โหลดเมนู 50 รายการพร้อมกัน 100 คำขอ | ผ่าน ประมาณ 189 ms; query รายการเมนู 1 ครั้ง และหมวดหมู่ 1 ครั้ง |
| ตรวจสถานะพร้อมกัน 100 คำขอ | ผ่าน ประมาณ 52 ms |
| ขนาดเมนูเต็ม / สถานะ | 10,975 / 149 bytes ในข้อมูลตัวอย่าง |
| ส่งจาก 100 โต๊ะพร้อมกัน | ผ่านครบ 100 รายการ ประมาณ 149 ms |
| ตรวจผลออเดอร์เดิมซ้ำ 20 ครั้งผ่าน API อีก instance | ไม่สร้างออเดอร์เพิ่ม |
| ยิง key ใหม่ถี่ 20 ครั้ง | บล็อกครบด้วย 429 ไม่เพิ่มออเดอร์ |
| ส่ง key ใหม่อันเดียวกันพร้อมกัน 20 ครั้ง | บันทึกเพียง 1 ออเดอร์ |
| เมนูปิดขายแล้วแต่แคชยังมี / โต๊ะปิดแล้ว | ปฏิเสธการสั่ง |

ทดสอบ browser ด้วย API จำลองแล้วว่าตะกร้าไม่หายเมื่อเมนูไม่เปลี่ยน, ไม่โหลดตามรอบเมื่อซ่อนหน้าเว็บ, ใช้เมนูเดิมหลัง reload โดยตรวจสถานะก่อน, เก็บ key เดิมหลัง 429 และล้างเมนูเมื่อโต๊ะปิด

เวลาทดสอบเป็นผลบนเครื่องพัฒนา ไม่ใช่ผลทดสอบ server จริง ต้องติดตาม latency, error, pool usage และ bandwidth ของ production เมื่อใช้งานจริง

รันทดสอบซ้ำ:

```bash
npm test -w backend
npm run check:ordering -w frontend
npm run test:ordering-capacity -w backend
```

ชุด capacity รันได้เฉพาะ DATABASE_URL ที่เป็น localhost และลบ schema ชั่วคราวของตัวเองเมื่อทดสอบจบ
